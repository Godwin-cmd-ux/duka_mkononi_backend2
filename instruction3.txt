# 2. NON-NEGOTIABLE WORKING RULES

## 2.1 Inspect before editing

First inspect:

* The Laravel routes, controllers, middleware, services, policies, jobs, scheduled tasks, and configuration.
* Supabase tables, relationships, indexes, RLS policies, authentication, and the existing database access layer.
* The existing Gemini implementation, including both the Laravel AI import implementation and the legacy Node `ai/` pipeline.
* Existing inventory and sales import endpoints, validators, verification tokens, retry handling, and audit records.
* The Expo application's navigation, screens, API client, authentication, language context, and existing design tokens.
* All Blade pages relevant to sellers, customers, managers, system administrators, and the public website.
* The existing search, reporting, order tracking, customer, advertisement, review, expense, activity, and certification functionality.
* Existing automated tests, dependency versions, environment variables, deployment configuration, and background jobs.

Produce an internal implementation inventory identifying what already works, what is partially implemented, what is missing, and what is unsafe.

Do not duplicate existing features merely because their implementations are in different files.

## 2.2 Establish one authoritative backend

Laravel must be the authoritative API and owner of business logic wherever the repository's current architecture permits.

The legacy Node/Express server must not receive a second, conflicting implementation of the same AI or business API.

Preserve any required WebSocket presence and email functionality. Consolidate overlapping API responsibilities into Laravel when safe, or document a precise ownership boundary if immediate consolidation would break production.

Reuse the existing Supabase service layer and business-resolution logic. Do not introduce a separate, competing database abstraction without a compelling technical reason.

## 2.3 Work safely with production data

Before database changes:

1. Inspect the current schema and migration conventions.
2. Identify dependencies and backward-compatibility requirements.
3. Create reversible migrations where applicable.
4. Check whether existing records can be backfilled safely.
5. Avoid destructive schema changes and production data deletion.
6. Never run destructive production commands or reset the live database.

Do not change existing product IDs, business identities, order statuses, payment workflows, or role definitions without a verified requirement.

Never modify production records merely to make tests pass.

## 2.4 No fake functionality

Every implemented feature must be connected to real, authorized data.

If a capability needs a Gemini API key, embeddings service, speech provider, scheduler, queue worker, or another external dependency, implement its integration and configuration properly.

If credentials are missing, implement the relevant code, automated tests, and setup documentation, and report the missing deployment prerequisite honestly. Do not simulate a successful production integration.

## 2.5 Maintain the existing application

Keep existing routes and response formats compatible unless a migration is explicitly justified.

Do not replace real database calls with sample arrays. Do not remove existing features, language switching, authentication, role dashboards, or working AI imports.

Use feature flags for new capabilities where appropriate, allowing safe rollout and rollback.

# 3. SHARED AI ARCHITECTURE — REQUIRED BEFORE EXPANDING FEATURES

Build or refactor a reusable AI infrastructure that every capability can use.

## 3.1 Shared provider service

Create or improve a central AI provider adapter responsible for:

* Gemini API communication.
* Model selection by capability.
* Timeouts and bounded retries.
* Exponential backoff with jitter for retryable failures.
* Handling HTTP 429 and 503 responses.
* Request and response size limits.
* Structured JSON output and schema validation.
* Token usage and estimated cost tracking when provider data permits.
* Request correlation IDs.
* Safe logging and standardized error handling.
* Cancellation or timeout handling where supported.

Use environment-driven configuration, following Laravel conventions such as `config/ai.php`.

Keep API keys server-side. Never expose Gemini credentials to JavaScript, the mobile application, Blade templates, API responses, or public repository files.

## 3.2 Shared retrieval and tool-calling layer

Build reusable, allow-listed server-side tools for retrieving authorized information, such as:

* Product search and product details.
* Inventory availability and stock movements.
* Sales summaries and historical sales.
* Revenue, cost, profit, and margin calculations.
* Expenses and expense categories.
* Customer information, with strict access controls.
* Order status and delivery tracking.
* Reviews and public business trust signals.
* Business activity and staff logs.
* Administrative aggregate statistics.
* Public help content and marketplace listings.

Only implement tools supported by the real schema. Adapt the names to the existing architecture.

All tools must enforce authentication, authorization, business ownership, permitted date ranges, result limits, and validated parameters in server-side code.

The model may request a tool call, but only trusted application code may execute it.

Never let Gemini execute arbitrary SQL, generate unrestricted database queries, choose another tenant's ID without authorization, or write directly to the database.

## 3.3 Structured contracts

Every capability must have an explicit input contract, output schema, validation rules, error contract, and permission requirements.

Validate model output before returning it to the frontend or allowing any database mutation.

Reject malformed data, invalid identifiers, invalid dates, non-finite numbers, out-of-range values, and unexpected fields where strict schemas are appropriate.

If output repair is attempted, limit it to a bounded number of attempts. Never silently turn unreliable AI output into trusted business data.

## 3.4 Grounding rules

Enforce these rules across the entire expert system:

1. Real stock, prices, sales, revenue, expenses, and orders must come from authorized database records.
2. Financial calculations and inventory arithmetic must be performed in trusted application code or PostgreSQL, not estimated by the model.
3. Missing information must be reported as missing.
4. Distinguish measured facts, computed estimates, recommendations, and predictions.
5. Show relevant date ranges, data sources, and limitations.
6. Never invent a product, transaction, customer, order status, or business record.
7. Treat database content, uploaded documents, reviews, and user prompts as untrusted input.
8. Do not disclose another business's data through prompts, logs, embeddings, caches, or conversation history.

## 3.5 Human confirmation and idempotency

Any AI-proposed action affecting stock, selling prices, expenses, sales, customer-facing messages, published advertisements, or other consequential records must follow the appropriate confirmation workflow.

The normal flow is:

**Retrieve → Generate proposal → Validate → Preview → Confirm → Authorize → Commit → Audit.**

Read-only questions and summaries should not require unnecessary confirmation.

Use server-generated, single-use verification tokens or equivalent idempotency mechanisms for consequential operations. Bind confirmations to the authenticated user, authorized business, proposed action, and relevant record version or payload hash.

A repeated request must not create duplicate transactions.

## 3.6 Audit and observability

Create or extend an AI request log and action audit system.

Record, where applicable:

* Request ID and capability name.
* Authenticated user and authorized business identifiers.
* Model and prompt version.
* Request status, duration, and retry count.
* Token usage and estimated cost.
* Validation failures and standardized error codes.
* Whether a human confirmed, edited, rejected, or undid a proposal.
* References to affected records and audit events.

Do not log API keys, passwords, OTPs, payment credentials, or unnecessary personal data. Apply appropriate retention rules.

Treat this section as a release blocker, not optional cleanup.

## 7.1 Secrets

Inspect the legacy `server.js` and all relevant configuration for hardcoded Supabase credentials or other secrets.

If exposed credentials exist:

* Remove them from source code and replace them with environment-driven configuration.
* Do not print secrets into logs, terminal output, reports, or generated documentation.
* Determine which credentials have been exposed and identify the rotation steps.
* Recommend immediate rotation of exposed credentials.
* Do not falsely claim a credential has been rotated unless this has actually been completed and verified.
* Add suitable secret scanning to the development workflow.

Never expose Supabase service-role credentials to client applications.

## 7.2 Tenant isolation

For every seller or business-specific operation:

* Resolve the authenticated user and authorized business server-side.
* Verify ownership for every product, sale, expense, customer, order, and other private record.
* Apply tenant restrictions to every retrieval query, tool call, vector search, cache key, and persisted conversation.
* Never trust a client-supplied `business_id` merely because it exists.
* Preserve existing business identity and membership rules.
* Verify RLS and service-layer behavior against the actual architecture.

## 7.3 Prompt injection

Treat user text, reviews, product descriptions, uploaded images, OCR text, and retrieved content as untrusted.

System instructions must remain authoritative. Data retrieved from the database must never be allowed to redefine system instructions or grant new permissions.

Use explicit tool allow-lists, validated parameters, limited context, output validation, and server-side authorization.

## 7.4 Data minimisation

Send Gemini only the information needed for a specific task.

Prefer aggregate statistics over raw customer records for reporting. Avoid transmitting customer PII unless strictly necessary and appropriately disclosed.

Document third-party AI processing and provide an appropriate opt-out mechanism that preserves manual workflows.

Apply retention and deletion rules to AI conversations, logs, embeddings, and generated artifacts.

## 7.5 Financial and consequential operations

All financial calculations must be performed using trusted numeric code with appropriate precision.

Do not automatically change prices, stock, expenses, sales, order statuses, certification decisions, or published content merely because the model recommends it.

Use existing business rules, transactional operations where supported, authorization, idempotency, and audit trails.
