 Duka Mkononi  (Gemini-Powered Expert System)

WHAT WAS BUILT
--------------
A read-only AI capability that reviews your business's products and tells you
which ones are LOSING money, have THIN margins, or are missing prices — with a
suggested selling price computed in trusted PHP (never guessed by the AI).

Endpoint:  POST /api/ai/price/suggest     (requires a logged-in seller/admin)

All money math happens in trusted code. Gemini only explains and prioritises,
and its output is sanitised so it can never invent a product, a price, or a
number.

  routes/api.php                            <- one new route
  tests/Unit/PricingAdvisorTest.php

STEP 0 — PREREQUISITES
----------------------
1. GEMINI_API_KEY must be set in .env   (it already is).
2. Start the API:      php artisan serve
   Base URL used below: http://127.0.0.1:8000
3. You need at least ONE active product that belongs to your business, ideally:
     - one product where selling price < buying price   (LOSS)
     - one product with a thin margin                   (THIN)
     - one product with no buying price                 (MISSING_COST)
   If you don't have these, you can still run the test and just check the shape.


STEP 1 — GET A TOKEN (log in)
-----------------------------
Replace the email/password with a real seller or admin account.

curl -s -X POST http://127.0.0.1:8000/api/login \
  -H "Content-Type: application/json" \
  -d '{"email":"SELLER_EMAIL","password":"SELLER_PASSWORD","role":"seller"}'

Expected: a JSON body containing  "message":"Login successful",  "token":"...".
Copy the token. In every command below, paste it after "Bearer ".

(WINDOWS USERS: if the single-quoted JSON is awkward in cmd.exe, run these in
 Git Bash, which the project already uses.)


STEP 2 — HAPPY PATH
-------------------
curl -s -X POST http://127.0.0.1:8000/api/ai/price/suggest \
  -H "Authorization: Bearer PASTE_TOKEN_HERE" \
  -H "Content-Type: application/json" \
  -d '{}'

EXPECTED (HTTP 200)
  {
    "success": true,
    "capability": "price_advisor",
    "locale": "sw",
    "currency": "TZS",
    "summary": {
      "product_count": <n>,
      "counts": { "LOSS": n, "ZERO_MARGIN": n, "THIN": n, "HEALTHY": n,
                  "MISSING_COST": n, "MISSING_SELLING_PRICE": n },
      "at_risk_count": <n>,
      "inventory_value_cost": <number>,
      "revenue_window": <number>,
      "margin_pct_window": <number|null>,
      ...
    },
    "products": [
      {
        "id": "...", "name": "...", "status": "LOSS",
        "buying_price": 1000, "selling_price": 900, "margin": -100,
        "suggested_price": 1200, "floor_price": 1100,
        "priority_score": <number>,
        "ai": { "severity": "...", "title": "...", "action": "..." }
      },
      ... sorted with the most urgent (LOSS) first ...
    ],
    "insights": [ { "product_id": "...", "severity": "high|medium|low",
                    "title": "...", "action": "..." } ],
    "watchouts": [ "..." ],
    "limitations": [ "...", "...", "..." ],
    "ai": { "available": true, "degraded": false, "code": null,
            "headline": "...", "meta": { "model": "...", "tokens": {...} } }
  }

WHAT TO CHECK
  [ ] success = true
  [ ] products[0] is usually a LOSS/THIN item (highest priority first)
  [ ] a LOSS item shows margin < 0 AND a suggested_price > buying_price
  [ ] suggested_price is a multiple of 500 (rounded up), never invented by AI
  [ ] limitations[] mentions any products with missing prices
  [ ] ai.degraded = false  (i.e. Gemini really answered)


STEP 3 — PARAMETERS
-------------------
Try a different language, window and target margin:

WHAT TO CHECK

 TEST FLOW — CAPABILITY #5: BUSINESS HEALTH SCORE & WEEKLY COACHING
 Duka Mkononi  (Gemini-Powered Expert System)
==============================================================================

WHAT WAS BUILT
--------------
A weekly, explainable business health digest. Four documented components —
margin, stock cover, sales trend and expense ratio — are scored 0–100 in
trusted PHP, weighted, and combined into one band. If there is not enough
evidence the app produces NO score at all (never a misleading one). Each digest
also lists meaningful changes vs. the previous week and up to three evidence-
based suggested actions, and is stored once per business + week so authorized
users can review the history.

Endpoints (all require a logged-in seller/admin)
  POST /api/ai/reports/weekly          generate / refresh a digest
  GET  /api/ai/reports/weekly          latest stored digest
  GET  /api/ai/reports/weekly/history  stored digest summaries
  POST /api/ai/health/setup            admin: create the storage table

Scheduled job
  php artisan ai:weekly-digests        (runs weekly per ai.health.delivery)

Files added/changed
  config/ai.php                                    <- health weights/thresholds/delivery
  app/Models/AiWeeklyDigest.php
  app/Services/Ai/HealthNarrator.php               <- 8-locale digest text
  app/Services/Ai/BusinessHealthScore.php          <- the score engine
  app/Services/Ai/HealthDigestService.php          <- retrieve + store (idempotent)
  app/Http/Controllers/Api/AiHealthController.php
  app/Console/Commands/GenerateWeeklyHealthDigests.php
  routes/api.php, routes/console.php
  tests/Unit/BusinessHealthScoreTest.php, tests/Feature/AiHealthRouteTest.php

FRONTEND (seller app + website, in all 8 languages)
  Duka_mkononi/app/muuzaji/afya-biashara.tsx   <- mobile screen (new tab)
  Duka_mkononi/app/muuzaji/_layout.tsx         <- registers the new tab

  * dismissals are per-account cache with a TTL and a cap, and the
    👍/👎 feedback feeds aggregate relevance counters (measurable
    feedback, counts only).

the catalogue emits stock / business_is_certified / image_url while the
gates read stock_quantity / is_certified and the cards show image - one

STEP 0 — PREREQUISITES
----------------------
1. Public catalogue rows: at least one PUBLIC business with an active
   product that carries a selling price and stock > 0 - the same rows
   GET /api/shop/products returns. (An empty catalogue honestly returns
   an empty feed.)
2. For the personalised path: a CUSTOMER account with at least one order
   (profile phone matching the order) and/or some liked ads; profile
   business_location is optional (it enables the "near you" reason).
3. No GEMINI_API_KEY needed: the ranking is pure code by design.
4. php artisan serve   (base URL http://127.0.0.1:8000)

QUICK SANITY (design guarantees)
--------------------------------
  * READ-ONLY for shared data: the feed never writes orders, stock or
    profiles; the only state it keeps is THIS account's dismissals
    (cache, TTL 90 days, capped at 100) and aggregate helpful /
    not-helpful totals.
  * Personal signals come only from the caller's own rows (orders matched
    via their account phone, their own likes, their own location); no
    customer's history can surface for another customer, and popularity
    is aggregate counts over a bounded window - never customer rows.
  * Hard gates run BEFORE ranking: public + available + in stock, and a
    dismissed id can never reappear; zero-score rows get an honest
    localized reason instead of a fabricated one.
  * The ranking is deterministic pure code (no model): score desc, name
    asc, id asc - identical inputs always produce the identical feed.
  * normalizeCatalogRow keeps the catalogue's real keys
    (stock / business_is_certified / image_url) in sync with the gates
    (stock_quantity / is_certified) and the cards (image) - pinned by
    unit tests on the REAL row shape.
  * Public read throttled 30/min; writes behind auth.jwt; feature flag
    ai.features.recommendations; every call audited (AI_RECO_*).

QUICK SANITY (design guarantees)
--------------------------------
  * Deterministic core: ReportSummary::summarize() is pure PHP over the
    rows BusinessDataProvider already returns for the report screens -
    the summary can never disagree with the tables above it.
  * Periods: the current window is truncated to COMPLETE days; the
    previous window is always the same length immediately before it.
  * Comparability: gross profit / margin compare only when BOTH windows
    carry a buying price for every sold line - otherwise the difference
    is disclosed instead of guessed.
  * Contributors are recorded revenue MOVEMENT between the windows,
    ranked by absolute change - described as movement, never as cause.
  * The model may only REWORD the same figures: every number in the
    reply must already exist in the data we supplied, bounded length,
    single paragraph - else the reply is discarded.
  * Scope: the caller's own business (member ids resolved server-side),
    admin/seller only; feature flag ai.features.report_summary; cached
    15 min per business + period + locale; every call audited
    (AI_REPORT_SUMMARY / AI_REPORT_SUMMARY_ERROR).

STEP 5 — GROUNDING SPOT CHECKS
------------------------------
1. Open the exact ad/product behind a finding: the excerpt must be a
   real substring of its title or description - never a paraphrase.
2. Fix the triggering text (lengthen a too-short description, remove a
   prohibited term), re-check: that finding disappears - findings never
   exist without matching rows.

QUICK SANITY (design guarantees)
--------------------------------
  * Deterministic first: severity comes from fixed rules run by trusted
    PHP (ReviewAssistant::reviewAd / reviewProduct). The AI only attaches
    an advisory verdict to a finding that ALREADY exists - it can never
    create, remove or re-grade a finding, its reasons are bounded and
    figure-free, and verdicts are accepted only from the allowed enum.
  * The decision endpoint RE-DERIVES the findings server-side, so a
    client cannot hide a violation to sneak an approve through, and it
    requires both the "I read the findings" confirmation and a written
    reason when rejecting definite violations.
  * approve -> published, reject -> unpublished, request edits ->
    unchanged; every decision is recorded (AI_REVIEW_DECISION) with the
    reviewer, the counts and the applied state.
  * Scope: the caller's own business (member ids resolved server-side),
    admin/seller only; feature flag ai.features.reviews; policy table
    configurable via config/ai.php (ai.reviews.*); results cached
    ai.reviews.cache_minutes (default 5) per business + target + locale;
    bounded to ai.reviews.max_items (default 200) items per check.
