# User Activity Monitoring, Audit Logging & Security Intelligence

This document describes the monitoring system added to DukaMkononi's Admin
module: what it records, where the data lives, how it is protected, how long
it is kept, and what it deliberately cannot know.

---

## 1. Purpose and principles

The system answers, with trustworthy evidence: *who did what, when, from
where, with what outcome - and what looks suspicious.*

Non-negotiable design rules (all enforced in code, not just here):

1. **Server evidence is authoritative.** Browser events are labelled
   `source: browser` and are observations, never proof that a database
   operation succeeded. Business mutations are audited server-side through
   the existing `AuditLogger` regardless of any browser listener.
2. **The actor is always derived server-side** (verified JWT / auth
   middleware attributes). A client can never attribute an event to another
   user - the ingest endpoint ignores any identity inside the payload.
3. **No credentials, ever.** Passwords, tokens, cookies, OTPs, reset codes,
   card/payment fields are redacted by key before any metadata is stored,
   and form/search listeners never read values in the first place.
4. **No invasive collection.** No keystroke logging, no pointer tracking, no
   clipboard/media/screen capture, no device fingerprinting. User-Agent
   parsing yields only browser/OS/device-class facts and always reports
   `Unknown model` for phones - models are never invented.
5. **Monitoring must never break the app.** Every write is best-effort:
   HIGH/CRITICAL failures are forwarded to the framework log (never
   silently discarded), everything else degrades quietly; dashboards show a
   setup banner instead of an error when the tables are missing.
6. **Existing data and flows are preserved.** `user_logs` keeps receiving
   exactly the rows it always did; the legacy logs endpoints and page view
   are untouched and still work.

## 2. Architecture

```
BROWSER                                   SERVER
dm-monitor.js (all pages,                 AuditLogger::log()  [existing call sites]
 one include in dm-locale)                      │ legacy row: user_logs (unchanged)
 - page/nav/visibility/scroll                    │ + mirror of MEANINGFUL actions
 - controls, fields, forms, search, files            │ (EventClassifier filters reads)
 - X-Correlation-Id on /api mutations               ▼
 - heartbeats, logout stop                   ActivityTracker::mirrorLegacy()
 - batched POST every ~12s                        │ sanitize + redact + derive actor
        │                                         │ UA parse, correlation, session
        ▼                                         │ risk assessment (SecurityMonitor)
POST /api/monitoring/events  (public,             ▼
  throttled, strict validation,               activity_events  ◄── MonitoringController
  actor from verified JWT only)                    ▲        (timeline/summary/detail/
        │                                     │     │         sessions/alerts/export)
        ├─ heartbeats ──► session_activity ◄──┤     └─ RecordAuthorizationEvents
        │                (last_seen, start     │        (403 / 419 / 429)
        │                 on login)            │
        ▼                                     └── SecurityMonitor.raiseAlert()
   ADMIN DASHBOARD                                  ▼
   /system_admin/dashboard                     security_alerts
   (Rekodi tab: Timeline | Security |          (one open incident per rule+subject,
    Sessions | Legacy)                          ack/resolve/notes, all audited)
```

**Why the bridge in `AuditLogger`:** ~300 existing call sites already audit
through one function. Extending that single point (instead of editing every
controller) gives full coverage of authentication, authorization, business
mutations and admin actions with zero duplication: the legacy row is written
first and unchanged, the normalized projection is a second, filtered step.
Reads/probes (`*_VIEW`, `*_FETCH`, `HEALTH_CHECK`, per-request
`AUTH_SUCCESS`...) are classified as noise and **not** mirrored.

## 3. Event schema (`activity_events`)

| column | meaning |
|---|---|
| `id` | uuid |
| `user_id` | actor from trusted server state, null for anonymous observations |
| `session_ref` | sha256(token)[:32] - server-derived, never the token itself; anonymous visitors get their own correlation id |
| `correlation_id` | `X-Correlation-Id` generated by dm-monitor for mutations, linking "clicked" → "server accepted/rejected" |
| `category` | authentication, authorization, account, admin, business, ai, system, page, navigation, input, control, search, form, file, session, security |
| `event_name` | SCREAMING_SNAKE id, allow-listed/normalized |
| `description` | human summary (single line, length-capped) |
| `page`, `route`, `element` | page title, **path only** (queries/hashes never stored), UI element label |
| `entity_type`, `entity_id` | business record touched, when the action names one |
| `source` | `server` (authoritative) or `browser` (observed) |
| `outcome` | success / failed / rejected / denied / observed |
| `severity`, `severity_reason` | INFO..CRITICAL **plus the reason it was chosen** |
| `is_security` | security events are separable from ordinary activity |
| `metadata` | sanitized JSON (redacted keys, bounded size) - before/after values from existing audit details pass through |
| `ip_address`, `user_agent`, `device` | server-observed source + parsed facts (`Unknown model` on mobile) |
| `created_at` | **server-generated** timestamp |

`session_activity`: `session_ref` (unique), user, start/last_seen/end +
status (`active`/`ended`/`expired`) and reason, IP, UA, parsed device.
Created on `LOGIN_SUCCESS`; refreshed by throttled heartbeats (browser
ingest and API requests, max one write/minute/session). `ended` is set from
a **browser-reported** logout observation - JWTs in this app carry no
expiry, so session end is never claimed as certain.

`security_alerts`: one open incident per `(rule, subject)` - repeated
failures bump `occurrence_count` instead of creating duplicates. Holds
severity, status (`open`/`acknowledged`/`resolved`), first/last seen,
summary, bounded context, investigation notes trail, who acknowledged/
resolved and the resolution.

## 4. Severity and risk rules (config/monitoring.php)

- Isolated failed login → INFO; second → LOW; then ladder steps:
  account MEDIUM@3 / HIGH@5 / CRITICAL@10; **privileged accounts**
  (admin, super_admin - legacy system_admin) MEDIUM@2 / HIGH@3 / CRITICAL@5; **source IP** ladder
  MEDIUM@6 / HIGH@12 / CRITICAL@30 - deliberately higher so one shared NAT
  never paints a single user as malicious.
- Authorization denials and rejected tokens use the IP ladder
  (MEDIUM@5 / HIGH@15 / CRITICAL@40 over 10 minutes).
- CSRF failures and rate-limit hits start at MEDIUM.
- Alerts open at `min_alert_severity` (default MEDIUM), aggregate per
  rule+subject while open, and record why (severity_reason) on each event.
- Flood suppression: at most 40 events per risk+source per 5 minutes are
  written (cache buckets), so a burst of rejected requests cannot become a
  burst of database writes; risk assessment results are cached 30s.

## 5. Retention

`php artisan monitoring:prune` (scheduled **daily** in `routes/console.php`):

| data | default window | env override |
|---|---|---|
| ordinary activity events | 180 days | `MONITORING_RETENTION_ACTIVITY_DAYS` |
| browser-observed events | 90 days | `MONITORING_RETENTION_BROWSER_DAYS` |
| sessions | 120 days | `MONITORING_RETENTION_SESSION_DAYS` |
| security events + alerts | **not auto-deleted** (365d only if explicitly enabled) | `MONITORING_RETENTION_SECURITY_DAYS`, `MONITORING_RETENTION_DELETE_SECURITY` |

Runs are bounded (batches of 1000, max 50 batches/night), delete in
sub-chunks of 100 ids, and write their own `MONITORING_PRUNED` audit record
(counts only) - the retention policy is itself auditable. Legacy
`user_logs` retention continues to use the existing admin cleanup endpoint.

## 6. Security of the monitoring system itself

- **Access:** every `/api/admin/monitoring/*` route sits inside `auth.jwt`
  *and* re-checks `role === 'admin'` server-side; failed attempts are
  audited (`ADMIN_MONITORING_UNAUTHORIZED`). Dashboard visibility is never
  the control.
- **Ingest hardening:** public but throttled (`monitoring.ingest.
  per_minute_limit`/min/IP, default 120), payload byte cap, per-request
  event cap, event/category/outcome allow-lists, path-only routes, string
  length caps, recursive metadata redaction (`password|token|secret|cookie|
  otp|card|cvv|...` keys → `[redacted]`), and array-parameter rejection.
- **No identity spoofing:** user identity comes only from
  `JwtToken::decode`; an expired/invalid token degrades to anonymous
  attribution instead of trusting the payload.
- **Output safety:** dashboard renders everything through `escapeHtml`;
  API responses never echo SQL/stack traces (monitoring endpoints answer a
  generic `unavailable` flag instead of exception details); CSV export
  neutralizes spreadsheet formula injection (`=`, `+`, `-`, `@`).
- **Audit-record protection:** activity/alert/session tables have no public
  write API (ingest can only insert `source: browser` rows with server-side
  actor); no endpoint lets anyone edit or delete events; alert status
  changes are themselves audited; deletion only through the scheduled
  retention command.
- **IP honesty:** `$request->ip()` is the recorded source. Configure
  `TRUSTED_PROXIES` (comma-separated IPs/CIDRs/`*`) behind a reverse proxy
  so Laravel's TrustProxies resolves the real client; any X-Forwarded-For
  value seen *without* trusted-proxy configuration is stored only as
  `metadata.forwarded_for_untrusted` and labelled in the detail panel.

## 7. Frontend instrumentation (public/js/dm-monitor.js)

- Loaded once from `partials/dm-locale.blade.php` (included by every page);
  document-level delegation covers dynamically rendered content, rerenders
  cannot duplicate listeners (single init guard).
- Records: page open/hidden/visible/close, route changes (history hooks +
  hash/popstate), scroll start + 25/50/75/90% milestones (throttled, once
  each, reset per route), field focus/blur/change (labels + types only,
  sensitive fields never content-monitored), form submit + client validation
  failures (no values), search submissions (**query text never recorded**),
  explicit `data-dm-track` controls + heuristic action words on
  buttons/chips/tabs (Swahili + English), file selection (count + extension
  only) and download requests, resource load failures (same-origin,
  path-only, capped).
- Transport: batches of ≤20 every 12s (queue cap 60), `keepalive` flush on
  `pagehide`, dedupe window 2.5s, network failures re-queue with a cap and
  stop after 8 consecutive failures, 4xx drops the batch (no retry loops),
  emission stops completely after logout (token removal detected on flush/
  heartbeat ticks and via `storage` events).
- Mutations to `/api/*` receive `X-Correlation-Id` (+ `X-DM-Source`), which
  the server stores on the mirrored audit event so detail panels can join
  browser intent with server outcome.

## 8. Admin dashboard (User Logs upgrade)

`/system_admin/dashboard` → **Rekodi** tab, four sub-views:

1. **Timeline** – summary cards (total events, logins, failed logins,
   high-risk, critical, failed business ops, admin changes, active users,
   open alerts) + server-side filters (user, category, severity, outcome,
   source, period, security-only, search) + server-side pagination + click
   for the detail panel (full description, severity + rationale, device/IP
   with trust label, outcome, correlation, session link, entity, sanitized
   metadata, related events by correlation/session).
2. **Security** – incidents by status (open/acknowledged/resolved), with
   acknowledge / resolve (resolution text) / reopen / investigation notes -
   every change audited - and "investigate" that pre-filters the timeline
   by the incident's subject.
3. **Sessions** – session list with device, IP, status, duration; detail
   shows its events and jumps to user investigation.
4. **Legacy** – the previous log view over `user_logs`, unchanged (old
   records stay readable; the old `/api/admin/logs*` endpoints are
   untouched, so existing consumers like the manager report page keep
   working).

User cards' **Logs** button now opens the server-side user investigation
(chronological events + that user's sessions), falling back to the legacy
local filter if the monitoring tables are missing. A setup banner
(`POST /api/admin/monitoring/setup`) creates the tables at runtime for
deployments that have not run migrations.

## 9. Deployment

1. **Tables:** `php artisan migrate` (creates the three tables), *or* press
   the dashboard setup button (same idempotent `MonitoringSchema::ensure()`),
   *or* `POST /api/admin/monitoring/setup` as an admin.
2. **Schedule:** ensure the Laravel scheduler runs
   (`* * * * * php artisan schedule:run`) so `monitoring:prune` executes
   daily.
3. **Environment (all optional, defaults are safe):**
   - `MONITORING_ENABLED` (default `true`) - master switch
   - `TRUSTED_PROXIES` - set when behind a reverse proxy (accurate IPs)
   - `MONITORING_RETENTION_*` - retention windows
4. **No new services, packages or paid dependencies** were added; storage
   reuses the existing Supabase/PostgREST path and Laravel cache.

## 10. Known limitations

- **Session end after browser disconnect** cannot be observed; JWTs carry no
  expiry, so `active` sessions age out by retention and client-reported
  logout is labelled `client_reported`.
- **Exact device models** are never claimed (`Unknown model`).
- **Anonymous browser events** (expired token, no token) are recorded
  without an actor - browser data is never presented as proof of person.
- **IP accuracy** depends on `TRUSTED_PROXIES`; without it the app records
  the address it can actually see and labels forwarded hints as untrusted.
- **PHP tests** in `tests/` follow the project's PHPUnit conventions and
  must be run in an environment with PHP + composer installed (this
  workspace has neither - see the final report).
- Events occurring outside the application (native phone UI, other devices,
  activity after a browser dies) are out of scope by design.
